一、任务描述
随着人工智能技术的快速发展，大语言模型（LLM）已在政务、法务、工程等多个领域得到广泛应用。水利行业作为国家基础设施建设和生态保护的重要领域，涉及复杂的技术标准和法律法规体系，涵盖国家标准、行业标准、地方标准以及配套的法律法规文件。如何高效理解、查询和应用这些规范性文件，成为水利工程设计、审查、监管与运维中的核心难题。
本项目旨在构建一个基于向量检索与大语言模型（LLM）结合的智能问答系统，用于对国家及地方水利标准与技术规范进行语义理解与精准回答。随着水利工程建设日益复杂，标准文件数量庞大、结构多样，传统基于关键词的检索手段难以满足工程技术人员对“语义相关”“结构化解析”“多源融合”的实际需求。本项目集成了300余项水利水电标准以及200余项水利相关法律法规。项目构建了一个智能问答系统，专门服务于国家及地方水利标准、法规和技术文档的语义查询任务。系统通过文本向量化检索（Chroma 向量数据.库）结合大语言模型（DeepSeek Chat），实现对用户自然语言提问的智能解答，适用于政府部门、工程设计院及科研单位的法规辅助检索工作，准确率较高。
二、国内外研究现状
1. 水利标准AI大模型
由水利部国科司组织中国水科院自主研发的基于多源语料的“水利标准AI大模型”正式发布，并在水利技术标准专题评估工作中实际应用。
该模型基于中国水科院“SkyLIM”体系，采用“海量知识库+DeepSeek/Qwen双模型+标准服务”技术架构，深度集成自然语言处理、知识图谱、多模态数据融合等技术，实现了水利标准立项、制定、实施与监督全生命周期数字化、智能化管理，填补了我国水利标准化领域智能化工具的空白，是水利标准化管理工作运用AI智能技术的最新成果。
该模型集成了1800余项水利水电标准，500余项水利相关法律法规、政策文件等，“十三五”“十四五”水利科研成果，《水利学报》《水科学进展》等核心期刊论文，以及28万项专利、近10年水利先进实用技术与科技成果推广目录等多源语料，并持续动态更新。搭载领域自适应的DeepSeek/Qwen双模型基座，通过专业训练，使其具备水利专业术语解析与水利标准专家级认知能力。基于先进语义算法，实现跨文本智能比对，具备水利标准AI智能查重比对、查询、编制、审查、评估、预测、宣贯等多维功能，有效提升标准的协调性、时效性和先进性。在实际应用中，查重比对准确率超96.7%，标准编制效率提高2.5倍，标准评估和审查效率提高3倍，标准检索准确率达99.5%以上，效率提高5倍以上，显著提升标准管理效能。（水科院，水利大模型）
2. WaterGPT
WaterGPT 主要应用于三个领域：（1）处理和分析水资源领域的图像和文本等数据；（2）支持水文任务的智能决策；（3）实现跨学科信息集成和基于知识的问答。该模型已取得显著成果。WaterGPT 的核心在于对监督微调阶段的训练数据进行精细划分，这些数据来源于真实世界数据，并使用人工方法和 GPT 系列模型注释进行高质量注释。这些数据被仔细地划分为四类：基于知识的、面向任务的、负样本的和多轮对话。（WaterGPT: Training a Large Language Model to Become a Hydrology Expert）
3.必要性
随着水利工程对标准化和法规执行要求的不断提高，传统检索手段难以满足工程实践中对语义理解与多源信息整合的需求，因此构建基于大语言模型（LLM）与向量检索结合的智能问答系统具有现实必要性和紧迫价值。当前已有如水科院的“水利标准AI大模型”与WaterGPT等项目在水利标准管理与水文智能问答领域取得成果，验证了AI模型在专业领域知识解析、标准查重、辅助决策等方面的显著能力。相比之下，本项目聚焦于国家与地方水利标准的语义查询与智能问答，填补在工程设计与法规检索场景中高精度、结构化、多源融合的应用空白，对提升水利行业的标准应用效率与智能化管理水平具有重要意义。
三、技术路线
 
1. 数据收集与知识库构建
•	数据来源：收集国家级和地方省市的水利技术标准、法规文本及表格数据；
•	数据预处理：
o	文本清洗与格式规整（去除噪声、分段处理）；
o	特殊结构（如表格）转化为 JSON 表示形式；
•	向量生成：
o	使用本地或部署式 Embedding 模型接口；
o	支持批量文本嵌入，构建语义向量。
2. 向量索引与存储管理
•	使用 Chroma 向量数据库 搭建本地持久化知识库，分为两类集合：
o	coll_cn: 国家级标准集合；
o	coll_loc: 地方标准集合；
•	支持 按省份、文件名、结构段落等标签分类管理；
•	提供高效的向量检索接口（Top-N 相似度查询）。
3. 问题理解与标准类型判断
•	采用 语言模型辅助推理（LLM），识别用户提问中的地域属性与标准适用范围；
•	自动分类为三类：
o	"cn" 国家标准；
o	"loc" 地方标准；
o	"special" 港澳台及国外标准（目前暂不支持）；
•	精准匹配所需的向量集合进行后续检索。
4. 相似文段检索与提示构建
•	对用户问题进行向量化后，使用 Chroma 检索相似文段；
•	将命中的多个上下文结果拼接，构造成一段带结构说明的提示（Prompt）；
•	引导语言模型对复杂文档（尤其是表格数据）进行结构解析与语义理解。
5. LLM 回答生成与返回
•	使用 DeepSeek Chat API 作为默认问答模型（可切换 OpenAI）；
•	输入由系统构建的提示信息，输出语义连贯、结构清晰的回答；
•	支持生成包含来源文献（文件名 + 页码）的答案说明，增强可溯性。

四、总体结构与模型选择
AGR机器人是一种结合了“知识检索”与“文本生成”的人工智能系统，它通过引入外部知识库来增强语言模型的回答能力，解决传统大模型“知识过时”、“内容幻觉”等问题。，以下是其优势与作用：
1. 优势
知识更新便捷
	AGR机器人能及时使用最新数据，通过实时或频繁更新的知识库，避免传统训练模型知识陈旧的问题。
高准确性与可靠性
	通过检索真实信息源并结合生成式AI的推理能力，AGR机器人能够提供准确且来源可追溯的回答。
快速部署与成本效益
	无需对模型频繁进行昂贵的重新训练，通过知识库更新即可实现信息更新，降低维护成本。
个性化与定制化
	可根据业务场景或用户需求快速调整知识库，实现针对特定领域或任务的深度优化。
增强交互体验
	提供更丰富和上下文感强的互动，提升用户满意度，适合高要求的客户服务或专业咨询。
2. 作用
智能客服
	快速、准确回答客户咨询，降低人工客服压力，提升客户服务效率。
企业知识管理
	帮助企业员工快速获取内部知识、文档或技术支持，提高生产力和决策效率。
教育与学习工具
	为学习者提供即时问答与个性化的教育支持，强化知识吸收效果。
医疗咨询辅助
	辅助医生或患者获取最新医学知识，支持医疗决策和健康管理。
科研与学术辅助
	帮助研究人员迅速查阅文献、文档，并生成高质量文献综述或研究总结。
	通过结合检索技术和生成模型，AGR机器人极大增强了智能助手的实用性、准确性和灵活性，能够有效支持各种专业场景的复杂需求。
3. 与其他形式对比
1. 与纯生成式大模型（如ChatGPT、GPT-4）比较：
特点	纯生成式大模型	AGR机器人
知识时效性	依赖训练数据，易过时	可实时更新知识库，保持最新
回答准确性	易受幻觉（hallucination）影响	结合事实检索，减少幻觉
成本与部署	高昂的训练与微调成本	部署和知识更新成本低
来源可追溯性	来源不明确	明确知识来源，便于验证
灵活性与定制化	相对低	高，可通过知识库定制

2. 与传统RAG（Retrieval-Augmented Generation）方法比较：
特点	传统RAG方法	AGR机器人
技术架构	检索模块简单，与生成模块分离明显	检索与生成深度融合，更智能
实时性与互动	通常静态知识检索	支持高互动性、实时知识更新
用户体验	常规交互	更流畅的上下文互动体验

3. 与纯检索系统（如搜索引擎、QA系统）比较：
特点	纯检索系统	AGR机器人
回答形式	提供现有文本片段或链接	生成更具体化、上下文的完整答案
交互体验	单向、简单的问答模式	交互性强，可进行深入对话
理解能力	浅层语义匹配	深层语义理解，能处理复杂问题

4. 与预训练微调模型（Fine-tuned LLM）比较：
特点	微调预训练模型	AGR机器人
更新成本	每次知识更新需重新微调，成本高	低，仅更新知识库即可
领域适应性	适应特定任务和领域	更灵活，支持多个领域动态适应
可解释性	一般较低	高，答案可回溯到具体来源

AGR（检索增强生成）机器人融合了检索技术和生成式AI的优势，相比于纯生成模型，它能实时更新知识库并降低信息幻觉问题；相较于传统检索系统，它具备更强的上下文理解能力，提升用户互动体验；而与微调预训练模型相比，它在知识更新成本与灵活性方面具有明显优势。总之，AGR机器人结合实时性、准确性、灵活性与低成本，能够广泛应用于智能客服、企业知识管理、教育辅助等领域，适用于多样化且高要求的智能交互场景。
4. 模型选择：主体模型
 DeepSeek Chat 是一个开源的高性能中文大语言模型，专注于提供智能对话和知识检索能力。以下是对它的深入介绍：
🚀 4.1） 模型背景与定位
DeepSeek 是由国内知名团队（例如 wei-ayaa、zhipeng-jia 等）联合开发的实用型大模型，版本命名为 “v3 0324”，其中 “0324” 表示模型训练截止于 2024 年 3 月 24 日的数据。
“free” 版本意味着完全开源，免费部署使用，无需商业授权。
🧠 4.2） 技术架构亮点
基于 Transformer 架构，并融合近年来优化技术，如 Flash-Attention、ALiBi 等，提高推理速度和内存效率。
支持 混合精度（FP16/BF16），可在常见 GPU 或 AI 加速卡上流畅运行。
🎯 4.3）功能特色
开放式对话能力：支持日常闲聊、扮演角色、写作润色等综合对话场景。
知识检索增强：内置本地或远程检索机制，增强事实查询能力，更适合提供及时、准确的信息。
定制能力强：可 fine-tune（微调）或 instruction-tune（指令微调），适配客服、教育、文档总结等垂直场景。
🧪 4.4）性能表现
中文理解与生成能力强，能处理复杂指令、多轮上下文与多任务场景。
依据测试测评，基础模型在多项中文测试集（如 CMRC、CLUE）表现超过原始 LLaMA3、Gemini 或其他中小规模模型。
在常见 GPU（如 A100、RTX 4090）上拥有高效的推理速度和较低延迟。
🛠 4.5） 使用方式简介
部署环境
推荐 Linux 系统下运行，有 CUDA 驱动环境的 GPU 优先。也支持在 CPU 或中小算力的 GPU 上使用，但速度略有下降。
 
5. 模型选择：主要组件
5.1) PaddleOCR 
PaddleOCR 是由百度 PaddlePaddle 团队开源的、基于深度学习的文字识别（OCR, Optical Character Recognition）工具库。它提供了从文本检测、方向分类、文本识别、版面分析到表格识别等完整的 OCR 流程，支持多种语言，覆盖通用、手写、场景、文档等多种应用场景。
主要特点
a)	全流程覆盖
o	文本检测（如 DB、EAST、SAST 等算法）
o	文本方向分类
o	文本识别（如 CRNN、Rosetta、SVTR 等多种模型）
o	结构化信息提取（如表格识别、版面分析等）
b)	高精度 & 高速度
o	支持多种高精度模型与轻量模型，兼顾准确率和推理速度。
o	提供量化、裁剪、蒸馏等优化方案，适合部署在移动端和嵌入式设备。
c)	多语言支持
o	原生支持中、英、日、韩、法、德、西、俄等80多种语言。
o	可自定义字典和训练识别新语言。
d)	易用性
o	一行代码即可完成OCR，无需复杂配置。
o	支持命令行、Python、C++、服务端和移动端部署。
o	社区活跃，文档丰富，案例齐全。
e)	丰富的拓展功能
o	支持表格识别（PaddleTable）、身份证/票据识别等专项场景。
o	支持图片、PDF、摄像头流、批量处理等多种输入方式。
典型应用场景
•	批量文档数字化（如档案、合同、简历、书籍）
•	行业票据、发票、身份证等结构化识别
•	场景图片中的文字提取（如广告、路牌、屏幕截图）
•	自然场景文本识别（如车牌识别、快递单号等）

6. 数据切片
6.1)	按页分段（Page-based Splitting）
做法
•	将原始文档按物理页（或 PDF 页）划分，每页作为一个独立 chunk。
•	通常会额外保留页码等元信息，检索后可直接定位回原文页。
优点
•	结构清晰：保留了文档的原始分页信息，方便检索时跳转到对应页。
•	较大上下文：一个 chunk 通常包含丰富语义，可减少跨 chunk 上下文丢失。
•	简单易实现：直接调用 PDF 阅读器或文档 API 即可获取每页文本。
缺点
•	Chunk 大小不均：有些页可能仅包含很少文字（如目录、空白页），有些页文字过多，导致 embedding 质量波动。
•	Granularity 较粗：如果一页涵盖多个主题或章节，查询返回后还需二次定位，检索精度可能下降。
•	篇幅过大风险：部分页文字超出模型上下文长度，需要再行二次拆分。
适用场景
•	文档结构明确、每页长度相近的报告、期刊。
•	需要精准定位到页码（如法律条文、专利检索）时优先。
________________________________________
6.2)	按字符分段（Character-based Splitting）
做法
•	固定字符数（如 500、1000 字符）为一段，必要时设置重叠（overlap）比例（例如 20%）保证上下文连续。
•	直接在字符边界切分，无视段落/句子结构。
优点
•	Chunk 大小统一：方便批量化处理，避免过长或过短文本；更好利用模型上下文窗口。
•	检索覆盖全篇：无遗漏，所有字符都被处理。
•	重叠机制灵活：可保证跨 chunk 的上下文衔接。
缺点
•	切点可能不在语义边界：可能在句子中间截断，导致部分 chunk 语义不完整，影响 embedding 质量。
•	后处理复杂：检索到 chunk 时，需要根据字符区间再定位到原文位置，增加映射成本。
•	对格式敏感度低：忽略了自然段、标题等结构信息。
适用场景
•	对上下文长度有严格控制的场景（如模型上下文窗口受限）。
•	文本格式多样、行/页分隔不规则的纯文本大规模处理。
________________________________________
6.3)	按空行分段（Paragraph/Blank-line Splitting）
做法
•	以空行（或多个连续换行符）为段落分隔符，将连续非空行视为一个 chunk。
•	通常再配合最大字符数限制和重叠，避免过长段落溢出。
优点
•	语义完整性高：自然段通常是一个独立论述单元，embedding 质量更好。
•	易于阅读与呈现：检索返回后，呈现给用户的段落结构清晰。
•	灵活可扩展：可加入更复杂的规则，如标题分层、列表处理等。
缺点
•	Chunk 大小不均：有些段落很短，有些段落很长，需要二次拆分或合并。
•	空行定义不一：不同文档格式中空行表现不一致，需预处理统一。
•	丢失页码信息：若原文很重视分页定位，需额外保存映射关系。
适用场景
•	自然语言文档（论文、报告、新闻、小说），段落之间语义界限明显。
•	用户检索希望看到连贯段落，而非断裂文字时。
6.4)	不同方法对比
特性	按页分段	按字符分段	按语句分段
语义完整性	中	较低（需重建）	高
Chunk 大小一致	否（页长差异大）	是	否（段落长短不一）
定位映射成本	低（有页码）	高（需字符映射）	中（可加位置标）
实现难度	最简单	简单	需要段落判定、段边识别
检索精度	中	高	高（自然段落）
适用场景	弱结构化文档	大规模纯文本排处理	自然语言内容、面向读者展示
